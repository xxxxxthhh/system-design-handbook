PART 3 · 分布式深水区 · 第 8 章

分库分表
以及热点分片

订单表过亿后，你把压力切成八份，以为容量终于线性增长。顶流场次开票时，其中一份却独自燃烧——均匀的哈希能搬数据，搬不走一个业务热点本身。

08 · 1 值班现场11:00，八个分片里只有一个在冒烟

创业第 2 年 8 个月，「秒抢」累计用户约 180 万。公司 130 人，后端 25 人。订单表突破一亿行后，慢查询连续霸榜；团队按 show_id 切成 8 个分片，常规查询终于恢复。两周后，顶流场次开票，11:00 整，大盘上七根柱子安静，一根直冲顶部。

林工摇头：「别先加第九台。取模扩容会让大部分订单搬家，8842 搬到新家后还是一个 key。」你需要先把热点从通用分片隔离出来，再决定扩容拓扑；否则在线迁移会与开票流量争 I/O，却不改变 62% 请求汇聚到一处的事实。

决策点 D1

此刻是 11:02。你的第一个动作是什么？

C 是教科书答案：先把热点从共享分片摘出来。 独立通道把 show_id=8842 的爆炸半径与普通订单隔离，入口配额保护其容量；若业务允许，再用用户或订单尾号分成子桶。七个健康分片不必陪热点一起迁移。

A 的问题是迁移成本和问题不对症。 取模从 8 变 9 会让约 8/9 的 key 改变目标，开票中搬动大部分订单会消耗网络与 I/O；热点 key 即使落到新节点，62% 的流量仍集中在一个分片。

B 会让事情更糟。 七个分片本来就有余量，扩大它们的池没有收益；shard-03 已 100% CPU，更大连接池只会放入更多并发争用，让排队从应用搬到数据库。

D 方向没错，但救不了现在。 索引能降低单次查询成本，值得复核；可眼前负载偏斜接近 5 倍，发布索引还要与在线写争资源。先隔离热点，再在安全窗口验证查询计划。

08 · 2 原理分片解决总容量，不保证业务均匀

分库分表把一张大表的行映射到多个物理分片。分片键决定每一行去哪，也决定每一种查询能否直接定位。若业务流量在 key 上极不均匀，哈希函数再均匀，也只能把这个热点完整地放到某一台机器。

最热分片负载 = 总负载 × 该分片 key 占比
热点判据：最热分片 / 平均分片 > 3

代入现场：总负载 80,000 QPS，show_id=8842 占 62%，因此承载它的分片至少收到 80,000 × 62% = 49,600 QPS。8 个分片平均是 80,000 ÷ 8 = 10,000 QPS，最热/平均为 49,600 ÷ 10,000 = 4.96，超过 3，明确进入热点区。

扩容还要付迁移账单。直接取模用 hash(key) % N 定位，N 改变时多数余数都会改变；一致性哈希只让新节点接管环上的一段 key 空间。对 N→N+1：

4 台扩到 5 台，取模约迁移 80%，一致性哈希约迁移 20%。一致性哈希降低的是拓扑变化带来的搬家量，并不自动保证每台负载平整。物理节点在环上位置有限，区间可能大小不一；因此要给每台配置许多虚拟节点，把大区间切碎后再分散。

分片键的账单比算法更长。按 user_id，用户订单历史是单分片查询，但一个热门场次会散到多个分片；按 show_id，场次售票统计和库存邻近，顶流场次却会压在单片。跨另一个维度的查询则要靠二级索引、映射表或 scatter-gather，读放大也随之出现。

选择 局部性收益 热点风险 补救手段
user_id 用户订单列表与售后查询单片完成 大客户或异常用户可能偏热，通常较易打散 热点用户独立桶、订单号路由映射
show_id 场次统计、同场订单处理集中 顶流场次天然形成业务热点 show_id + bucket、热点场次独立通道

分片键是未来查询与热点的契约。选它时不要只问“数据能不能均匀”，还要问“业务最热的那个 key 会把多少请求带到同一台机器”。

热点分片是第 5 章缓存击穿的另一副面孔：许多并发围绕同一个 key 汇聚，只是这次被击穿的不是缓存回源，而是分片容量。第 12 章会为顶流场次设计独立通道，把它从普通订单漏斗里摘出来。

08 · 3 病历卡平均值很好看，单柱已经烧红

热点分片

病历卡 No.10
Hot Shard · 业务热点被稳定映射到单个分片
机理
分片键分布或访问频率不均，一个高频 key、租户或时间段集中落到同一分片。集群总容量仍有余量，但最热分片先耗尽 CPU、连接或 I/O，其他节点无法自动分担。
症状
▁▁▁█▁▁　单柱独高型。集群平均 CPU 与 P99 看似可控，单片指标却显著高于其余分片；最热/平均超过热点判据，错误集中在特定 key 或租户。
易发场景
按 show_id 分片遇到顶流场次；按时间分片导致最新分区承接全部写入；大租户独占一个 key；递增 ID 的错误范围切分；虚拟节点过少造成环区间不均。
处方
① 热点隔离：独立通道与资源池；② 二次打散：在业务 key 后追加 bucket；③ 虚拟节点：平滑一致性哈希区间；④ 按分片观测：告警最热/平均，而不是只看集群平均。
案例
「秒抢」8 个订单分片总计 80,000 QPS，顶流 show_id=8842 占 62%，shard-03 独自承接 49,600 QPS；最热/平均达 4.96，其余七片仍有余量。

看到 ▁▁▁█▁▁，先停止看集群平均。按分片、key、租户和访问模式下钻，算出最热/平均；若只是扩容而不改变热点 key 的映射方式，新机器很可能只接走冷数据。

08 · 4 模拟器扩容时，到底要搬多少 key

用固定的 10,000 个 key 对比取模与一致性哈希：先看扩容迁移量，再看虚拟节点如何修平负载，最后用单个热点 key 击穿两种方案。

🧪 3 个实验（按顺序做）

  1. 扩容搬家。取模模式用 4 台点「扩容一台」，再重置、切一致性哈希后重做 → 取模迁移约 80%（75%–85%），一致性哈希约 20%（12%–30%）。两者迁移量级分别接近 N/(N+1) 与 1/(N+1)。
  2. 修平环。一致性哈希下把虚拟节点从 1 调到 150 → 最大负载/平均严格下降，150 时低于 1.30。一致性哈希天然不均匀，虚拟节点是必需品。
  3. 注入热点。把节点数设为 5，打开「注入热点 key」，分别观察取模与一致性哈希 → 两种模式的最热分片/平均都超过 2。分片解决容量，不解决热点；热点要靠第 5 章的击穿处方与打散。

⚖️ 这个模型简化了什么

  • 「迁移比例」只数 10,000 个等重 key 的迁移个数，不计数据字节量、QPS 或复制因子。模型把每个 key 当成等权重的一份 → 真实迁移成本取决于要搬的字节数、当时的读写流量和副本数，而不是 key 的个数 → 因此不要把这里的「12%–30%」直接当成你系统扩容时要迁移的数据量或流量比例。
  • 30% 热点是单个合成 key 人为注入的，不是从真实访问日志采样出来的分布。模型只制造一个超重 key → 真实热点通常是随时间变化的多 key Zipf 分布 → 因此不要用这次演示得出「一致性哈希能把热点压到 2 倍以内」之类的保证，热点打散仍要靠专门处方。
  • 150 虚拟节点下 <1.30 的负载比，是这一组随机哈希函数和这批样本 key 的结果。换一批 key 或换一个哈希函数，具体数值会变化 → 唯一稳定的是「虚拟节点越多、分布越均匀」这个方向性结论 → 因此不要把「150 个虚拟节点、<1.30」当成可以直接照抄的生产配置，要用自己的 key 分布重新测。
  • 模型只演示了「加虚拟节点」这一种均匀化手段。它没有对比 bounded-load、rendezvous hashing 等替代方案 → 现代生产系统也常用这些方法达到均匀，不一定靠堆虚拟节点数量 → 因此不要得出「一致性哈希的不均匀只能靠加虚拟节点解决」的结论。

这些简化是故意的：模拟器的目的是隔离一个因果关系，不是预测生产数值。 实验清单里的每条现象都由 tools/simN-*-model-test.js 的断言保证， 但保证的是这个模型里的现象。

08 · 5 权衡按用户聚拢，还是按场次聚拢

分片键要服务主访问路径。user_id 让用户订单天然聚在一起，show_id 让场次订单天然聚在一起；复合分桶则用更多路由复杂度换热点打散。三个方案都能落地，但每个都会把另一类查询变贵。

决策点 D2

订单主表的分片键怎么选？

A · user_id：用户订单历史、退款与售后通常单片完成，用户分布相对容易均匀。 账单：按场次统计、核销和批量处理要跨片聚合，需二级索引或异步数仓；大客户仍可能形成局部热点。适合以用户查询和售后为主的订单系统。

B · show_id：同场订单局部性好，场次统计与批处理简单，和场次级业务天然邻近。 账单：顶流场次把读写压到单片，用户订单列表要跨片查询；热门程度越偏斜，容量越难预测。适合场次均匀、场次级处理远多于用户查询的系统。

C · show_id + bucket：保留场次维度的可定位性，同时把一个顶流场次拆到多个子分片。 账单：同场统计要聚合多个 bucket，桶数扩缩、路由表和事务边界更复杂；冷场次也可能被过度拆分。适合热点场次占比高、可接受聚合成本的秒杀通道。

「秒抢」的选择：普通订单主表采用 A，优先保障用户订单、退款和售后；顶流开票走 C 的独立热点通道，而不是让普通表都为极端场次付复杂度。理由是用户查询是长期主路径，热点场次则应被明确隔离；第 12 章会把这条独立通道放进完整秒杀架构。

08 · 6 复盘没有搬全城，先给热点单开一条路

回放 11:00 的正确剧本——先隔离正在燃烧的 key，再处理查询成本，扩容迁移留到流量稳定之后：

11:02

隔离热点。入口识别 show_id=8842，切到独立限流队列与临时热点库；shard-03 到达量从 49,600 降到 18,200 QPS，普通订单错误率开始回落。

11:06

场次内打散。新订单按 user_id 尾号拆成 8 个 bucket，并保持订单号到 bucket 的路由映射；热点通道最热/平均从 4.96 降到 1.42。

11:13

恢复普通分片。限制迁移与后台统计，给 shard-03 排空慢查询；其 CPU 从 100% 回到 58%，订单 P99 从 6.4s 降到 390ms。

12:20

计划性扩容。流量回落后评估一致性哈希与虚拟节点，用影子路由核对 4→5 的迁移范围；扩容不再与开票请求争同一条 I/O 通道。

壹
集群平均会掩盖单片死亡。容量告警要同时看最大值、分位数和最热/平均比；平均 CPU 低不代表每个分片都有余量。
貳
扩容不是热点处方。新节点能接走一部分普通 key，却不会拆开单个业务热点；先隔离或二次打散，再谈机器数量。
叁
分片键会向未来收税。它决定查询局部性、跨片聚合、扩容方式和热点形态；选择前要列出主路径与最坏流量分布。

08 · 7 自测你看的是平均，还是最热那一柱

Q1 · 看形状诊断

六个分片的负载形状呈 ▁▁▁█▁▁，集群平均正常，错误集中在一个业务 key。最可能是？

A。单柱独高且绑定特定 key，是 No.10 的形状。D 很诱人，因为入口突发也会抬高负载，但均匀突发通常让多片一起上升；题中只有一片燃烧，证据指向分布偏斜。

Q2 · 迁移算术

从 4 台扩到 5 台，取模与一致性哈希的迁移比例量级分别约是多少？

B。取模约 4/5=80%，一致性哈希约 1/5=20%。A 是诱人的错误项，它把“新增一台占五分之一”直接套给取模，却忽略了模数改变会重排多数余数。

Q3 · 热点算术

总负载 90,000 QPS，某 key 占 40%。它所在分片至少承担多少 QPS？

C。90,000 × 0.4 = 36,000。D 很诱人，因为把 40% 看成了 40,000，但百分比必须乘总量；B 则像是把总量平均分成四份，忽略题目给出的 key 占比。

Q4 · 分片键账单

订单按 user_id 分片后，哪类查询最可能需要额外的跨片聚合或二级索引？

B。同一场次的用户分散在多个 user_id 分片上，场次统计需要跨片或额外索引。A 是最诱人的错误项，但它正是 user_id 分片的局部性收益：一个用户的订单可直接定位到单片。

🎯 面试映射 · 本章直接覆盖的高频追问

「分库分表方案怎么设计？」 答题骨架：容量与查询画像 → 选择分片键 → 路由与全局 ID → 扩容迁移 → 跨片查询与事务 → 按分片观测和回滚。
「热点 key 怎么处理？」 答题骨架：算最热/平均 → 识别业务 key → 限流与隔离 → 二次 bucket 打散 → 缓存击穿保护 → 热点消退后的合并与回收。
「分片键选错了怎么补救？」 答题骨架：先加映射层或二级索引止痛 → 双写新旧路由 → 回填校验 → 灰度切读 → 停旧写并回收。反直觉加分点：先量迁移比例和热点分布，不把扩容当重分片。
