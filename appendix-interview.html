章节高频追问答题骨架锚点链接
第 1 章「估算一下这个系统需要多少台服务器 / 多大容量。」答题骨架：先要 DAU 和人均请求数（没有就自己假设并说出来）→ 日请求量 → 平均 QPS → 乘峰值倍数（说明为什么这个业务取这个倍数）→ 再用 并发 ≈ QPS × RT 折成机器数 → 最后单独说一句存储和带宽。反直觉加分点：主动指出峰值形状比总量重要，并问一句「这个业务的流量是平缓型还是尖峰型」。第 1 章 →
第 1 章「讲一下从用户点击到看到结果，中间经过了什么。」答题骨架：DNS → 建连（TCP + TLS 握手，强调来回次数）→ 反向代理 → 应用（路由/鉴权/业务）→ 数据库（连接池 → SQL → 事务）→ 原路返回。每一环补一句「这里可能慢在哪」，并点出数据库通常是最贵的一环。第 1 章 →
第 1 章「一开始就该上微服务吗？」答题骨架：不按偏好答，按信号答 → 团队规模与发布冲突频率、变更频率差异、故障隔离需求 → 说明单体在小团队下的真实优势是"函数调用而非网络调用" → 给出拆分的触发条件而不是时间表。可以主动说：拆分不降低复杂度，只是把它从代码搬到网络上（第 13 章会展开）。第 1 章 →
第 2 章「为什么不能无限加大连接池？」答题骨架：池是并发许可 → 下游容量才是吞吐上限 → 大池把等待搬到 DB → 实例数 × 单池大小核算总连接 → 用压测找安全水位。第 2 章 →
第 2 章「为什么 P99 比平均值重要？」答题骨架：平均值会稀释长尾 → 排队由慢请求占槽传播 → 对比 P50/P99 与超时比例 → 用分位数定位少量请求如何拖住资源。第 2 章 →
第 2 章「超时应该怎么定？」答题骨架：从端到端用户预算倒推 → 参考正常 P99 而非拍脑袋 → 给各层分配 deadline → 明确取消与重试 → 用错误率和资源释放验证。反直觉加分点：超时首先是资源预算。第 2 章 →
第 3 章「主从延迟导致读到旧数据，怎么办？」答题骨架：先按业务定义可接受新鲜度 → 圈出关键写后读 → 强制读主 / 会话粘性 / 乐观展示三选或组合 → 给出主库容量与失败回滚账单。第 3 章 →
第 3 章「复制延迟怎么监控？」答题骨架：主库提交位点 → 副本接收位点 → 副本应用位点 → 区分网络与重放 → 补业务 write-to-visible 的 P50/P99 → 按新鲜度目标告警。第 3 章 →
第 3 章「读写分离的路由放哪一层？」答题骨架：列应用层 / 数据访问层 / 代理层责任边界 → 比较业务语义感知、统一治理与故障切换 → 用写后读标记贯穿路由。反直觉加分点：路由不只是负载均衡，它也在执行一致性契约。第 3 章 →
第 4 章「缓存一致性方案怎么设计？」答题骨架：先定权威源与可接受窗口 → 选 cache-aside 等模式 → 写顺序与失败补偿 → 热点回源保护 → 版本比对与业务对账。第 4 章 →
第 4 章「为什么先删缓存再写库也有坑？」答题骨架：画并发时序 → 删除后读 miss → 读到旧 DB 值并回填 → DB 新值提交 → 缓存遗留旧值 → 给出二次失效或改顺序的账单。第 4 章 →
第 4 章「延迟双删值不值？」答题骨架：它缩小特定并发窗口 → 延迟长度依赖读耗时与复制延迟 → 第二次删除仍可能失败 → 不能替代重试和对账。反直觉加分点：先量错误窗口，再决定是否加复杂度。第 4 章 →
第 5 章「Redis 突然全挂了，系统会发生什么？怎么办？」答题骨架：契约公式说明 DB 将承受多少倍流量 → 止血（限流降级）→ 恢复（高可用切换/重启）→ 预热 → 慢放量 → 复盘单点问题。能主动讲出「冷缓存死亡螺旋」是强信号。第 5 章 →
第 5 章「穿透、击穿、雪崩的区别与对策？」别背处方，先讲症状形状（渗血 / 尖刺 / 断崖）再对症给药——展示的是诊断能力而非记忆力。第 5 章 →
第 5 章「命中率降到多少需要告警？」反直觉加分点：不看命中率绝对值，看 总流量 × (1 − 命中率) 相对 DB 容量的余量。命中率 90% 在小流量系统里岁月静好，在大流量系统里已经着火。第 5 章 →
第 6 章「限流算法怎么对比与选型？」答题骨架：先给已验证配额 → 描述令牌桶尖头 / 漏桶直线 / 滑动窗口台阶 → 匹配突发容忍度 → 给队列、状态与公平性账单。第 6 章 →
第 6 章「降级预案怎么设计？」答题骨架：按资金与履约分 L0/L1/L2 → 每层写开关、兜底数据和用户文案 → 独立资源隔离 → 定期演练恢复顺序。第 6 章 →
第 6 章「限流阈值怎么定？」答题骨架：压测容量 → 扣除故障与长尾余量 → 按核心链路最窄处设总预算 → 生产指标校准 → 分级动态调整。反直觉加分点：阈值不是机器峰值，而是可持续服务承诺。第 6 章 →
第 7 章「重试为什么会把小故障放大？」答题骨架：画调用层 → 写乘积公式 → 代入 3×3×3=27 → 解释资源占用制造更多超时 → 给单一责任层、预算与幂等前提。第 7 章 →
第 7 章「熔断和限流有什么区别？」答题骨架：限流按容量控制进入量 → 熔断按失败状态停止某依赖 → Closed/Open/Half-open → 两者与降级、舱壁组合。第 7 章 →
第 7 章「backoff 的 jitter 有什么用？」答题骨架：backoff 把峰向后摊开 → 相同参数仍会同步醒来 → jitter 随机打散 → 说明它不减少总量。反直觉加分点：预算与 jitter 分别管总数和波形。第 7 章 →
第 8 章「分库分表方案怎么设计？」答题骨架：容量与查询画像 → 选择分片键 → 路由与全局 ID → 扩容迁移 → 跨片查询与事务 → 按分片观测和回滚。第 8 章 →
第 8 章「热点 key 怎么处理？」答题骨架：算最热/平均 → 识别业务 key → 限流与隔离 → 二次 bucket 打散 → 缓存击穿保护 → 热点消退后的合并与回收。第 8 章 →
第 8 章「分片键选错了怎么补救？」答题骨架：先加映射层或二级索引止痛 → 双写新旧路由 → 回填校验 → 灰度切读 → 停旧写并回收。反直觉加分点：先量迁移比例和热点分布，不把扩容当重分片。第 8 章 →

第 9 章「消息积压了怎么办？」答题骨架：生产/消费差值定方向 → oldest age 定影响 → 限制非核心生产 → 找消费瓶颈 → 按分区与下游余量扩容 → 算追平时间 → 清零后对账。第 9 章 →
第 9 章「消息顺序性怎么保证？」答题骨架：先问全局还是业务键内有序 → 同 key 路由同分区 → 单分区串行或版本校验 → 重试不允许状态倒退 → 说明热点键与吞吐账单。反直觉加分点：多数订单系统需要的是聚合内有序，不是全局排队。第 9 章 →

第 10 章「预扣库存和实际库存怎么对账？」答题骨架：初始配额 → 预扣凭证 → 订单落库 → 支付状态 → 取消释放 → 按业务键做差集 → 超时未知先查询再补偿。说明对账不变量与人工处置入口。第 10 章 →
第 10 章「Redis 挂了，库存怎么办？」答题骨架：先停止新增批准 → 明确 RDB/AOF 与副本恢复边界 → 用已落库订单和预扣凭证重建 → 对账后慢放量。反直觉加分点：库存服务降级应偏向少卖，不能在状态未知时绕过权威账继续收款。第 10 章 →

45 分钟怎么分配

系统设计面试通常给 45 分钟，多一分钟都没有。下面是一份可执行的节奏表——不是死规矩，是给你一个默认锚点，防止在某一段里超支到收不了尾。

阶段建议分钟数这一段要产出什么
需求澄清5 分钟功能范围 + 非功能约束（QPS 量级、延迟目标、一致性要求）+ 明确说一句「这次不做什么」。
容量估算5 分钟DAU/QPS/存储量级 + 峰值倍数，说出假设，不用算到小数点。
API 与数据模型7 分钟2–3 个核心接口签名 + 关键实体和它们的索引/分片键。
总体架构10 分钟组件框图 + 数据流箭头，边画边讲每个组件的职责一句话。
瓶颈深挖10 分钟面试官追问的那一个点讲透——通常是缓存、分片、一致性或削峰里的一个，不用四个都展开。
可靠性与故障5 分钟指出架构里的单点，给出降级/兜底动作。
收尾3 分钟权衡总结一句话 + 主动说一条「我知道但没时间展开」的短板。

5 维评分尺

下面这把尺子不是给面试官用的，是给你自己练完一题后回看用的。每一档写的是可观察的行为，不是形容词——你应该能对照自己刚才说的话，逐条打勾。

怎么定档：每一档写的都是比上一档多做到的事；「够用」格写的是最常见的短板，「良好」「优秀」写的是补上它之后的样子。从「够用」往上看，你的档位是最后一个你完整做到的档——只命中一句「优秀」却没做到「良好」的条目，仍然只算「够用」。如果某道题根本没触发某个维度（比如题面里没有失败场景），该维记 N/A，不要记 0，也不要用它拉低整体判断。

维度够用良好优秀
需求与约束说出了功能范围和大致 QPS 量级，没有主动问延迟或一致性要求。主动追问了非功能约束（延迟、一致性、可用性），并明确说出了「这次不做什么」。把约束翻译成了后续设计的判据（例如「读多写少、能容忍秒级新鲜度，所以后面允许用缓存」），并在设计里真的用上了这句话。
估算与容量算出了 QPS 量级，用乘法得出结果，但没检查数量级是否合理。给出 DAU → QPS → 峰值倍数 → 机器数区间的完整链条，并说明了每一步的假设。指出了哪个假设最敏感（换一个数量级，结果会差多少），并说明了下一步用什么压测去缩小这个不确定性。
架构与数据流画出了组件，但无法从入口开始逐条边走到最终的读/写结果；至少有一条关键边没有说明协议、数据或状态变化。边画边讲清楚了完整数据流，并标出了读路径和写路径的差异。主动标出了架构里当前最可能先倒下的那条边，并说明了为什么先怀疑它而不是别的组件。
失败与恢复提到了「要限流」「要重试」这类通用词，没有映射到架构里的具体组件。针对架构图里某个具体依赖，说清楚了它变慢/挂掉会发生什么，以及第一层兜底动作。讲出了故障传播路径——哪个下游变慢会拖垮哪个上游——并给出了阻断点，而不是给每个组件逐个贴创可贴。
