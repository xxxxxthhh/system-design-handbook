## 五个模拟器规格

### Sim-1 · 排队论（第 2 章）→ `assets/sim-1.js` / `tools/sim1-queue-model-test.js`
- **教学目标**：利用率 ρ 不是效率指标，是风险指标；P99 在 ρ→1 时起飞；超时是止损单。
- **控件**：到达 QPS（滑块）、单请求服务耗时 ms（滑块）、并发数/连接池大小（滑块）、超时 ms（滑块）
- **模型**：服务能力 `cap = 并发数 / (服务耗时/1000)`；`ρ = 到达QPS / cap`。
  排队延迟用 M/M/c 直觉近似：`W_queue ≈ 服务耗时 × ρ/(1−ρ)`（ρ≥1 时队列无界增长，
  用一个显式的队列长度状态量累积，别直接除零）。
  P50 ≈ 服务耗时 + 0.7×W_queue；P99 ≈ 服务耗时 + 4×W_queue（给出一个稳定的分位近似即可，
  重点是形状对，不是精确排队论）。超时到达时请求被丢弃并计入错误率，同时**释放并发槽**。
- **图**：P50 折线、P99 折线、利用率 ρ（%）折线、超时错误率（%）折线；画一条 P99 阈值线。
- **实验清单（3 条）**：
  ① 把到达 QPS 调到让 ρ ≈ 50% → 80% → 95%，记录 P99 三次读数。结论：ρ 线性上涨，P99 指数上涨。
  ② 保持 ρ ≈ 95%，把并发数**调大一倍**。结论：吞吐几乎不变（瓶颈在服务耗时不在槽位），
     但排队更深、P99 更糟——「无限加大连接池」是幻觉。
  ③ 保持过载，把超时从宽（如 3000ms）收紧到窄（如 300ms）。结论：错误率上升，
     但**存活请求的 P99 显著下降**，系统从「全员慢死」变成「部分快速失败」。
- **必须断言**：
  - ρ=0.5 / 0.8 / 0.95 三点的 P99 满足 `P99(0.95) > 4 × P99(0.5)`
  - ρ≈0.95 时并发数翻倍：稳态吞吐变化 < 10%，且 P99 不下降（≥ 原值）
  - 超时 3000→300：错误率上升，且已服务请求 P99 下降 > 50%
  - 极端值（QPS 最大 + 服务耗时最大 + 并发最小 + 超时最小）跑 2000 tick 无 NaN/Infinity

### Sim-3 · 限流算法对比（第 6 章）→ `assets/sim-3.js` / `tools/sim3-ratelimit-model-test.js`
- **教学目标**：同一波突发注入三种算法，**形状不同就是选型依据**。
- **控件**：突发倍数（滑块）、基础 QPS（滑块）、配额 limit（滑块）、令牌桶桶深 burst（滑块）、
  「注入突发」按钮、暂停/重置
- **模型**：三条独立通道同时消费同一到达序列
  - 令牌桶：容量 `burst`，速率 `limit`/s；有令牌就放行 → 突发初期可放行一大段
  - 漏桶：恒定流出 `limit`/s，队列有上限；输出**恒平**，超出队列的丢弃
  - 滑动窗口：窗口 1s 分 10 格滚动计数，窗口内已放行 < limit 才放行
- **图**：三条「放行 QPS」折线 + 一条到达 QPS 折线 + 配额线；被拒曲线用同色虚线或第二组线
- **实验清单（3 条）**：
  ① 点「注入突发」，看三条放行曲线形状：令牌桶有一个尖头后回落到配额；漏桶全程一条直线；
     滑动窗口在窗口边界呈台阶。结论：形状 = 对突发的态度。
  ② 把桶深从小调到大，重复注入。结论：桶深就是「你愿意替下游承担多少突发」，
     桶深越大放行尖头越高——**桶深是把突发转嫁给下游的旋钮**。
  ③ 把配额调到低于基础 QPS。结论：三者稳态放行量都收敛到配额，差别只在瞬态；
     稳态下**限流算法之争是个瞬态问题**。
- **必须断言**：
  - 突发窗口内令牌桶累计放行 > 漏桶累计放行
  - 漏桶输出方差 < 令牌桶输出方差（漏桶更平）
  - 桶深翻倍 → 突发期令牌桶放行峰值上升（严格大于）
  - 稳态（无突发）下三者放行量都 ≈ min(到达, 配额)，相对误差 < 10%
  - 极端参数无 NaN/Infinity

### Sim-4 · 重试风暴（第 7 章）→ `assets/sim-4.js` / `tools/sim4-retrystorm-model-test.js`
- **教学目标**：`末端放大倍数 = ∏(每层重试次数)`；backoff+jitter 改变的是**波形**不是总量。
- **控件**：调用层数（1–4）、每层重试次数（1–4）、backoff 开关、jitter 开关、
  下游故障率（滑块）、「注入下游故障」按钮
- **模型**：一次入口请求在第 k 层失败后重试 `r` 次；末端收到的请求数 = `r^layers`（失败全量重试时）。
  故障率 p 下的期望放大 = 逐层展开。backoff 关时所有重试**同刻发出**（波形是尖峰）；
  开 backoff 后按 2^n 间隔错开；jitter 再加 ±50% 随机扰动把同刻峰摊平。
- **图**：末端到达流量随时间（尖峰 vs 摊平），另一条线画「放大倍数」
- **实验清单（3 条）**：
  ① 层数 1→2→3，每层重试 3 次，看末端放大倍数 3 → 9 → **27**。结论：重试是**指数**不是加法。
  ② 保持 3 层 ×3 次，开 backoff。结论：放大总量不变，但峰值被拉平——
     backoff 治的是**瞬时峰**，不治**总量**。
  ③ 再开 jitter。结论：同刻重发的同步性被打散，峰值进一步下降（这就是病历卡 No.08 惊群效应的解药）。
- **必须断言**：
  - 层数 1/2/3、每层 3 次时末端放大倍数分别 ≈ 3 / 9 / 27（相对误差 < 5%）
  - 开 backoff 后：末端**累计**请求数与关 backoff 相比变化 < 10%，但**峰值**下降 > 40%
  - 开 jitter 后峰值再次下降（严格小于只开 backoff 的峰值）
  - 层数=1 且重试=1 时放大倍数 = 1
  - 极端参数无 NaN/Infinity

### Sim-5 · 一致性哈希（第 8 章）→ `assets/sim-5.js` / `tools/sim5-hashring-model-test.js`
- **教学目标**：扩容迁移比例的量级差；虚拟节点治不均匀；热点 key 谁都治不了。
- **控件**：节点数（3–8）、虚拟节点数/节点（1–200）、key 总数（固定 10000 即可）、
  「取模 / 一致性哈希」切换、「扩容一台」按钮、「注入热点 key」开关
- **模型**：用确定性哈希（自己写一个 FNV-1a 或简单 32 位混合函数，**不许用 Math.random 做 key 哈希**，
  否则测试不可复现）。取模：`hash(key) % N`。一致性哈希：环上二分查找。
  迁移比例 = 扩容前后归属发生变化的 key 占比。
- **图**：左半区画环（canvas 圆 + 节点刻度 + key 密度），右半区画每节点负载柱状图
- **实验清单（3 条）**：
  ① 取模模式，4 台扩到 5 台，读迁移比例 ≈ **80%**；切一致性哈希重做，≈ **20%**。
     结论：`取模迁移 ≈ N/(N+1)`，`一致性哈希迁移 ≈ 1/(N+1)`。
  ② 一致性哈希、虚拟节点数从 1 调到 150，看柱状图从参差不齐变齐。
     结论：一致性哈希**天然不均匀**，虚拟节点是它的必需品不是可选项。
  ③ 打开「注入热点 key」（把 30% 流量压到单个 key 上）。结论：无论取模还是一致性哈希，
     单点柱子照样爆——**分片解决容量，不解决热点**（热点要靠第 5 章的击穿处方 + 打散）。
- **必须断言**：
  - 取模 4→5 的迁移比例 ∈ [0.75, 0.85]
  - 一致性哈希（虚拟节点 150）4→5 的迁移比例 ∈ [0.12, 0.30]
  - 虚拟节点 1 → 150：`最大分片负载/平均负载` 严格下降，且 150 时 < 1.30
  - 注入热点后最热分片负载/平均 > 2（两种模式都成立）
  - 哈希函数确定性：同一 key 两次调用结果一致；测试可复现（无 Math.random）
  - 极端参数无 NaN/Infinity

### Sim-6 · 积压水位（第 9 章）→ `assets/sim-6.js` / `tools/sim6-backlog-model-test.js`
- **教学目标**：`积压增速 = 生产 − 消费`；`追平时间 = 积压 ÷ (消费 − 生产)`；
  消费速率只差一点点也会积压到天亮。
- **控件**：生产速率（滑块）、单消费者速率（滑块）、消费者数（滑块）、
  「开票洪峰」按钮（一段时间生产速率 ×5）、暂停/重置
- **模型**：`backlog += (produce − consume×consumers) × dt`，下界 0。
  给出「按当前速率追平还需 T」的实时估算（消费 ≤ 生产时显示「永不追平」）。
- **图**：积压水位折线（主）、生产速率线、总消费速率线；标一条「积压告警线」
- **实验清单（3 条）**：
  ① 把总消费速率设为生产速率的 **95%**，静置。结论：只差 5% 也会**线性且不回落**地涨——
     这就是病历卡 No.11 的 `▁▂▃▄▅▆▇` 形状，它**不会自愈**。
  ② 点「开票洪峰」制造一段积压，然后把消费者数**翻倍**，读追平时间。
     结论：追平时间 = 积压 ÷ 净消费速率，扩容效果**可以算出来**，不用猜。
  ③ 把消费者数调到远超生产（如 3 倍）。结论：积压清零后继续加消费者**没有任何收益**——
     消费者数的上限由分区数/下游写入能力决定，不由积压决定。
- **必须断言**：
  - 消费 = 0.95×生产、跑 600 tick：backlog 单调不减且末值 > 初值 ×5
  - 制造积压 B 后消费者翻倍：实测追平耗时与 `B/(consume−produce)` 相对误差 < 10%
  - 消费 > 生产时 backlog 收敛到 0 且**不为负**
  - 消费者从 3 倍加到 5 倍：追平时间下降但积压清零后吞吐不再上升（受生产速率限制）
  - 极端参数无 NaN/Infinity
