## E1 我的作答（写于展开基准答案之前）

作答时手上只有：ch16 的题面文字 + 那块保障群屏幕 + 附录 A 的病历卡编号表。
剩下 4 分钟就上架（题面说 5 分钟后，我按写完这页答案花掉 1 分钟算）。

### ① 一页容量契约

**先说结论：我算不出一个可用的绝对数，我能交的是一个「以第 2 批实测值为锚」的相对契约。**
下面第一版就是拿来证明为什么不能用绝对数的。

**第一版（纯假设推导，用来自证不可用）**

| 变量 | 含义 | 我的取值 | 来源 |
|---|---|---|---|
| `U` | 口播瞬间在线人数 | 下界 8万 / 上界 35万 | **题面给的** |
| `c` | 听到「补货了」后真的点抢的比例 | 下界 30% / 上界 60% | **我猜的**，无依据 |
| `r` | 人均连点次数（前端若无防连点） | 下界 1 / 上界 4 | **我猜的**，依据第 11 章「狂点八次」 |
| `w` | 点击集中的时间窗 | 3 秒 | **我猜的** |

```
QPS_peak = U × c × r / w

下界 = 80,000 × 0.30 × 1 / 3 =   8,000 QPS
上界 = 350,000 × 0.60 × 4 / 3 = 280,000 QPS
```

**上下界差 35 倍。** 一个跨 35 倍的区间在容量规划上等于没有区间：按下界准备会被打死，
按上界准备今晚也来不及。所以这一版的产出不是数字，是一句话——
**我缺的不是算力，是一个实测锚点，而这个锚点现在就有：第 1、2 批已经发生过。**

**第二版（可复查的契约，我真正交的那份）**

设 `Q2` = 第 2 批上架后 10 秒内的入口峰值 QPS（**待测，第 1 分钟就去拉**）。

```
规划值   Q_plan  = 1.5 × Q2     # 第 3 批「数量更大」的影响
防护阈值 Q_guard = 2.0 × Q2     # 限流挡板设在这里
```

倍数 1.5 的理由（这是假设，不是事实，请复查）：数量变大**不直接**抬高在线人数
——在线人数由直播决定，不由库存决定。它抬高的是**留存**：库存多 → 用户觉得「这次有戏」→
放弃率下降、连点次数上升。所以我预期峰值高度涨得不多，**峰的宽度和二次尖峰涨得更多**。
如果实测发现 Q3 > 2×Q2，说明我这条推理错了，请按「口播措辞变了/推流被外部转发了」重新找因。

**两条独立的容量线（我认为这才是这道题真正的容量契约）**

```
有效流量上界 = 本批库存数 N        # 成功扣减最多 N 次，这是硬上界，与流量无关
无效流量     = Q_peak − N/w        # 剩下的全是「注定失败」的请求
```

秒杀系统的容量问题从来不是「怎么服务完 Q_peak」，是
**「怎么让 (Q_peak − N) 那部分尽可能便宜地失败」**（第 12 章）。
所以容量验收标准我写成：**售罄快速失败路径的单请求成本 ≤ 正常扣减路径的 1/10，
且不落 DB、不进 MQ。** 这条比 QPS 数字更可复查。

**我卡住的地方（如实写）**

- **缺机器数与单机容量**：题面只给了「P99 43ms、无告警」，没给库存服务实例数、
  Redis 规格、连接池大小。所以我**无法回答「够不够」**，只能回答「相对第 2 批涨了多少」。
  这是本题我最大的空洞——一份说不出「够不够」的容量契约，严格讲是半份。
- **缺「监控里到底有没有第 2 批的曲线」**：我的整个第二版契约压在 `Q2` 上。
  题面告诉我「二次尖峰倍数没人测过」「缺口没人统计」，那 `Q2` 大概率也没现成看板。
  如果连入口 QPS 的历史曲线都没有，**我这份契约就地作废，且我在 4 分钟内没有 Plan C**。

### ② 架构草图（文字）

我不知道波普工坊实际链路，只能按全书拼出的那张图 + 第 12 章秒杀方案**假设**一条，
并把我不确定的地方标成岔路：

```
直播间 App
  └→ CDN / 静态资源（商品页、图片）
  └→ 网关（鉴权 · 限流 · 秒杀接口单独一条限流规则）
       └→ 秒杀入口服务
            · 前置：本地缓存的「售罄标记」→ 命中直接 fail-fast，不往下走
            · 幂等键（用户 + 批次 + SKU），拦住连点        ← 第 11 章
            · Redis 原子扣减（Lua / DECR），单 SKU = 单 key ← 热点，见风险
       └────────┬──────── 岔路 A：同步 RPC 调订单服务
                └──────── 岔路 B：投 MQ，订单服务异步消费   ← 第 9 章
            └→ 订单服务 → 订单 DB（分库分表，按 user_id）
                 └→ 支付服务 → 【第三方支付渠道】← 唯一我不控制的一段
                      └→ 支付回调 → 订单状态机 → 库存最终确认
            └→ 超时未支付回收任务（定时扫描 → 还库存）
```

**我标出来的三道裂缝（都是题面逼出来的，不是我凭空加的）：**

1. `Redis 扣减` 与 `订单创建` 之间**没有共同事务**——这是题面「库存扣减成功但订单创建失败」
   直接告诉我的。而且用户看到的是「已扣」而不是「抢失败」，说明**失败后没有同步回补库存**，
   要么靠回收任务兜底，要么根本没兜底。
2. 岔路 A 还是 B 我判断不了，但**两条岔路的处方不同**：A 是同步失败要补偿，
   B 是消息确认边界（No.12）。**题面没有任何一句话能让我区分**，我只能两条都准备。
3. 支付渠道是唯一的外部依赖，也是唯一我今晚改不动的东西。所有止血动作必须假设它不变。

### ③ 前三个风险

**风险一 · 库存被吞（扣了但订单没建，也没还回来）· 病历卡 No.12（消息丢失与重复）**

- 机理：确认边界与业务提交不在同一原子事务里，题面已经观测到这类记录了。
- 为什么排第一：它**不会报警**（症状 `▁▁▁▁▁`，只有对账），而且损失不可逆——
  5000 件里被吞掉的那部分，今晚卖不出去，明天也补不回来。第 3 批量更大 = 吞得更多。
- **如果我错了会看到什么信号**：跑一次对账，`Redis 已扣数 − 订单已创建数 − 已回滚数`
  在第 2 批尖峰后 60 秒内回落到 0（说明回收任务在正常工作）。回落到 0 = 我判断错，
  这只是个短暂窗口，不是漏。**长期非零且单调增 = 我判断对。**

> 编号选择上我不太自信，写下来：**没有一张卡是直接讲「跨服务部分提交」的**。
> No.12 的机理写的是消息确认边界，如果这里是岔路 A（同步 RPC），
> 严格说 No.12 套不上，No.03 讲的是缓存/DB 双写也套不上。我是**挑了个最近的**。

**风险二 · 支付缺口是超时重试放大，不是渠道拒绝 · 病历卡 No.07（重试风暴）**

- 机理：支付渠道变慢 → 客户端/服务端重试 → 渠道更慢 → 用户看到转圈又手动重试。
  题面的「转圈很久最后失败」正是这条曲线的用户侧描述。第 3 批更大 → 直接踩深。
- 为什么排第二：它是**唯一一个会自我放大**的风险，而且已经有零星证据了。
- **如果我错了会看到什么信号**：对比入口 QPS 与到渠道的末端 QPS——
  比值**稳定不爬升**，且渠道返回码里「明确拒绝/风控/限流」占比高而「超时」占比低，
  那就是渠道在拒绝，不是我们在放大。**那样处方完全不同**（要找渠道方，不是调重试）。

**风险三 · 尖峰过后不恢复 · 病历卡 No.16（亚稳态故障）**

- 机理：第 3 批量更大 → 队列积压 + 重试 + 支付超时互相喂养，流量回落后系统留在坏态。
- 为什么排第三：它是前两个风险的**合并症**，单独发生概率低，一旦发生今晚就结束了。
- **如果我错了会看到什么信号**：调出第 2 批尖峰后的曲线，若各项指标在几十秒内
  **自行**干净回到基线，说明当前负载还在稳定区，这条风险可以降级。
  这个验证**现在就能做**，不用等第 3 批。

**（写完发现该进前三但被我挤掉的：No.10 热点分片。）**
单 SKU 就是单个 Redis key，5000 件全在一个 key 上，这是教科书级热 key。
我把它放第四是因为「P99 43ms 无告警」说明它现在没热到出事——但这个理由其实不硬，
因为前两批的量比第 3 批小。**这一条我自己不太服气，记下来。**

*止血（改状态，不改代码）*

  **建议今晚只放剩余库存的一部分**——因为没有 fail-fast 就意味着 (Q_peak − N) 全部打到后端。
- 支付侧：把服务端对支付渠道的重试次数**调低**（若可配），并确认有退避。宁可让用户手点，

*明确不做*

**决策门（写死，免得到时候心软）**
> 第 3 批上架后 60 秒内，若「扣减 − 订单」缺口 > 该批数量的 1%，

  它既不是扩容也不是限流，它是**改业务侧的到达过程**——不拒绝任何用户，只把峰摊平。
  这是我认为在 5 分钟窗口里最有性价比的动作，而这道题不接这个答案。

**按任务书要求记下来：这就是分支选择的第一个问题——它预设了「扩容 vs 限流」这组二选一，
而全书教给我的最优解（削峰、改到达过程、第 9 章削峰填谷）不在选项里。**

**第二个问题：我 E1 写死的决策门当场失效。** 我设的是「缺口 > 该批数量的 1% 就停播」。
E2 才告诉我基线缺口是 **10%**——两个分支都远超我的门槛，**连分支 Y 这个「好结局」也触发我停播**。
不是我的门槛离谱，是 E1 题面只说「少一截」没给量级，我只能拍一个。
**一道要求「可复查」的题，却把复查所需的基线藏到下一阶段才给。**

下面按 **分支 Y** 作答（我离它更近）。

### ① 更新后的前三风险排序

**掉出去的：No.16 亚稳态故障。**
Y 分支里缺口稳定在 10% 不发散，尖峰过后没有出现「流量回落但系统留在坏态」的特征。
我 E1 里给它写的反证信号（指标能自行回到基线）在这里被满足了。降为观察项。

**新冒出来的（我认为是本阶段最重要的一条）：用户看到的状态与系统真实状态不一致。**
弹幕截图「显示无库存」。这有两种完全相反的成因，处方也完全相反：
- (a) **被限流拒绝的请求，被前端渲染成了「无库存」**——错误码语义污染。
  真实库存 > 0，是我们自己把它显示成 0 的。这时运营的质问是对的。
- (b) **Redis 里真的是 0，因为库存被吞了**（我 E1 的风险一）。这时运营的质问方向是错的，
  放宽限流不但没用，还会加速把剩下的库存也吞掉。

**注意「别的平台同款仍在售」这条证据我不采信**——那是不同的库存池，
它既不能证明我们有货，也不能证明我们没货。**这是题面里的诱饵，我把它剔除。**

**新的前三：**
1. **假售罄 / 状态失真**（勉强挂 **No.15 灰色故障**：聚合指标全绿、局部子集已经在报错。
   这里的「局部子集」是被拒的那批用户）。直接损失营收，且当场无法自证清白。
2. **10% 的缺口是「流量无关的固定失败率」**（No.12 / 或根本是渠道契约问题）。
   **依据就是 Y 分支本身**：限流让流量下来了，缺口一动不动。
   如果它是过载引起的，收紧流量必然让它下降。它没降 → 它不是过载。
3. **库存被吞（No.12）保留但降级到第三**：Y 分支没给我任何关于库存回补的证据，
   我仍然不知道「扣了没建」的那部分还没还回来。**降级不是因为它变小了，
   是因为我在 Y 分支里拿不到判断它的证据**——这本身要记账。

**（No.07 重试风暴也从前三掉出去了：限流后缺口没扩大，说明目前没有放大回路。）**

### ② 最想补的一条监控

**把「用户看到售罄」这一个渲染结果，拆成三个互斥的按秒计数器：**

```
真实售罄     (Redis 本批余量 == 0)
被限流拒绝   (网关 429 / 候选配额未中)
扣减失败其它 (超时、异常、幂等冲突)
```

选它的理由：**这一条监控同时回答两个人的问题。**
运营问「是不是控太死」→ 看 429 占比；我问「库存是不是被吞了」→ 看 Redis 余量是否真为 0。
把 E1 里那个我分不清的岔路（a/b）一次切开。

**如果改不了前端埋点，退而求其次的一条：**
`Redis 本批剩余库存` 与 `本批已创建订单数` 两条曲线同屏。
`本批数量 − 剩余 − 已创建订单` 这个差值就是被吞掉的量——一条曲线顶一次对账。

### ③ 接下来 5 分钟（止血，不重新设计）

| # | 动作 | 类型 |
|---|---|---|
| 1 | **查一次 Redis 本批剩余量**（10 秒的事）。这是整个判断的分水岭 | 诊断 |
| 2 | 若余量 > 0 且 429 占比高 → **把限流阈值放宽一档（放宽，不是取消）**，同时盯缺口 | 止血 + **受控实验** |
| 3 | 若余量 == 0 而运营坚称还有货 → 这不是限流的锅，是库存被吞。**立即停第 4 批**，转对账止损 | 止血 |
| 4 | 回复运营：暂不采信「别的平台在售」这条依据，我按 Redis 余量决策，2 分钟内给结论 | 沟通 |
| 5 | 不扩容、不改代码、不清缓存 | — |

**第 2 步值得单说：我在把限流阈值当探针用。**
放宽一档之后，如果缺口从 10% 往上走 → 缺口里含过载成分；
如果纹丝不动 → 确认它是流量无关的固定失败率，今晚调什么容量参数都救不了它，
要去查渠道返回码。**这是分支 Y 独有的机会——我能主动制造一次对照实验，
而分支 X 那边流量已经上去了，做不了这个对照。**

### 我看出的「两个分支相通」的地方（题面提示要自评这一点）

两边的病灶都不在库存服务，都在**扣减之后**的那一段。真正相通的是**同一个量的两次读数**：

- **X（流量上去了）**：缺口 10% → 23%，**随流量涨** → 缺口里有过载成分。
- **Y（流量下来了）**：缺口稳定 10%，**不随流量动** → 缺口里有固定成分。

**这两个读数合起来才能把 10% 这个缺口拆成「过载的部分」+「本来就会失败的部分」。**
单独看任何一个分支都拆不开——所以从诊断角度说，
**这道题让我二选一，恰恰剥夺了我把它拆开的能力。**
我在 ③ 里用「放宽一档看缺口动不动」自己造了另一半读数，
就是为了把 X 分支不让我拿的那个数据点补回来。

**顺带：X 分支里那句「15 秒后订单自动取消，库存又跳回 +1」信息量极大——
它直接证明了补偿机制存在且在工作，也就是我 E1 风险一的反证信号成立。
而 Y 分支没有任何一句话能替代它。** 选 Y 的人拿不到这个答案。
如果这两段现场只能读一段（题面说「只有一段和你有关」），
那么**选 Y 的读者会带着一个错误的风险排序离开这道题**——
他不会知道库存其实还得回来。我是因为「两段都读完再挑」才捡到的。

### 我对 E2 基准的三点异议

**1.（技术性异议，我认为这条是硬的）基准的监控在分支 Y 上是盲的。**
基准选「库存扣减成功时间戳 → 订单最终状态确认时间戳」的差值分布 P50/P99，
并声称它「能同时回答分支 X 的『缝有没有变宽』和分支 Y 的『限流有没有误伤』」。

前半句我同意。**后半句不成立**：限流误伤的是**被 429 挡在门外、根本没走到扣减那一步的用户**。
这些请求**不会产生「库存扣减成功时间戳」**，因此完全不在这个分布里。
一个只统计「已经扣减成功者」的指标，看不见「没能扣减的人」——
而分支 Y 的全部争议恰恰就在后者身上。
要回答运营那句「是不是控得太死」，必须去数被拒的人，这条指标数不到。

我认为正确答案是**两条都要**：基准那条量「缝有多宽」，我那三个计数器量「门口挡了谁」。
基准把它压成一条「性价比最高的指标」，在 Y 分支上把读者带偏了。

**2. 基准把「加自动补偿」放进了 5 分钟止血动作里，和它自己 E1 的纪律冲突。**
自评清单第 3 条的原文示例是「接下来 5 分钟的动作是不是止血（**比如给已知缝隙加补偿**或告警）」。
加补偿逻辑 = 改代码 = 发版。E1 基准刚教育过我「现在还不知道该往哪个方向调，不要动参数」，
关卡三（Knight Capital 四十五分钟）整篇讲的就是仓促上线的代价。
**直播进行中、5 分钟窗口内往库存链路加补偿，是这本书自己反复警告的那类动作。**
（加告警/计数器我同意，那是只读的。补偿不是。）

**3. 事实错误：「不能照抄第 3 章的处方」应为第 4 章。**
基准原文说 No.03 的双写分叉思路「不能照抄**第 3 章**的处方」。
但附录 A 里 No.03（缓存与 DB 双写不一致）的展开章节写的是
**第 4 章 · 上缓存——以及你签下的一致性契约**；第 3 章是读写分离与复制延迟（那是 No.02）。
这是把**卡号 No.03 当成了章号第 3 章**。
我作为读者真的会去翻第 3 章，然后发现讲的是主从延迟，一头雾水。
