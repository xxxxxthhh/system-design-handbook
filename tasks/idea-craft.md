## 1. 移动端

### 问题 M1（本视角最重的一条）：模拟器 canvas 在窄屏下被各向异性拉伸，抹掉的正是"形状即诊断"最依赖的陡峭线段

`assets/style.css:107` `canvas{width:100%;height:250px}` 把 CSS 显示高度锁死在 250px，
不随容器宽度变化；而 6 个模拟器章节（ch02、ch05–ch09，`grep '<canvas'` 逐一核对）的
canvas 元素内部绘图缓冲区固定是 `width="1760" height="500"`。

实测（本地起 `python3 -m http.server`，用 iframe 把 ch05.html 塞进 375px 宽容器测量
`getBoundingClientRect()`）：

- 375px 视口下，canvas 实际渲染框是 **285×250**，缓冲区是 1760×500 →
  水平缩放 0.162，垂直缩放 0.50，**各向异性比 3.08×**
- 桌面宽度（.wrap 760 − 22×2 padding − .sim 20×2 padding ≈ 676px）下渲染框约
  676×250 → 水平缩放 0.384，垂直缩放 0.50，各向异性比只有 1.3×，肉眼看不太出来

因为整张 canvas 位图是按 CSS 尺寸做非等比拉伸（不是重新绘制矢量），`assets/sim-2.js`
里 `ctx.lineWidth=3` 画的 err/hit/off 三条折线（第 159-170 行），在陡峭（接近垂直）的
线段上会被压到约 0.162×3 ≈ **0.49 CSS px 宽**——低于可视像素，视觉上会糊掉或消失；
平缓线段仍有约 1.5px，看得见。陡峭线段恰恰对应"DB 瞬间崩溃""缓存雪崩尖峰"这类
全书反复强调"形状=诊断"的关键形态。容量虚线（`ctx.setLineDash([10,8])`，
sim-2.js:155）同理：10px 划线 + 8px 间隙在移动端变成约 1.6/1.3 CSS px，低于可辨识
的虚线分辨率，读者被教着去看的"容量虚线"在手机上基本看不出是虚线。
6 个模拟器共用同一套 CSS 规则和同一种 1760×500 缓冲区（逐一 grep 确认），问题不是
个例。

**建议做什么：** 让 canvas 缓冲区尺寸响应式（在 `reset()`/`resize` 时按容器实际渲染宽度
和 `devicePixelRatio` 重设 `cv.width`/`cv.height`，而不是写死 1760×500），这样缓冲区与
CSS 显示框始终同比例，不再各向异性拉伸。纯 CSS 端（`style.css:107` 加窄屏断点调整
`height`）只能治标，治不了拉伸本身。

**为什么值得做：** 这正是 README.md「已知限制」里作者自己承认没做过的检查——
「未做浏览器目检……建议发布前在真机上翻一遍 6 个模拟器页面」。这次做了，而且结果
比"看起来更方"更严重：是渲染层面的降质，不是审美意见。`tools/css-audit.py`
的检查范围（读过全文，第 1–6 项）只覆盖未定义 class、裸色值、资源引用、表格横向
滚动容器、模拟器 id 对齐——完全不具备渲染几何检测能力，这类缺陷天生在现有 8 道
自动校验之外，不是"漏做"，是这类检查本来就不是脚本能做的事。

**工作量：中。** CSS 部分小；6 个 sim 文件的响应式 canvas 尺寸改造是主要工作量
（结构相同，可以写一次模式复用），改完需要在 375/768/1024 三档手动回归看 6 个
模拟器的折线是否清晰、容量虚线是否可辨。

### 已核实、不是问题：架构图 `.arch` 在 700px / 768px 下的表现

brief 点名问了 `.arch`。实测 ch12（全景图，6 个节点）在 700px 和 768px 两档
iframe 容器下，`.arch-flow` 的 clientWidth/scrollWidth 都是 820/933（不随容器宽度
变化——因为节点尺寸是内容驱动的，允许超出父容器由 `.arch` 的 `overflow-x:auto`
接住），且 `documentElement.scrollWidth - clientWidth === 0`，即溢出被正确地
限制在 `.arch` 内部横向滚动，没有撑破整页。换句话说：这张图在桌面宽度下同样需要
横向滚动才能看全，700–768px 并不是一个额外被破坏的"平板死区"，是这个组件本来
就该有的、和 `.tbl-wrap` 表格一致的横向滚动兜底模式，在这个宽度区间工作正常。
560px 以下另有媒体查询把它切换成纵向堆叠（`style.css:198`），体验更好，但
700–768px 没有新缺陷，不需要动。

ch01 的基线图（6 个节点、内容更窄）在 700px 下完全不溢出（clientW === scrollW
=== 610），同样正常。

### 已核实、不是问题：`.case-row` / `.tbl-wrap` / `.toc-item` / `.sliders` 的窄屏断点

`.case-row`（560px 断点转单列）、`table.tbl`（`.tbl-wrap` 横向滚动 + 首列
`min-width:118px`，这是 285d90b 已修的）、`.toc-item`（560px 转单列，8d9cb79 已修
拉伸的 tag-pill）、`.sliders`（560px 转单列）——逐条读代码 + 375px 实测，均正常。
这两个近期 commit 已经把最容易在窄屏踩坑的两处堵上了，不用重复劳动。

## 2. 可访问性

### 问题 A2：`--faint` 令牌在其实际使用场景下不满足 WCAG AA 对比度，且与项目自己的硬性要求冲突

用 WCAG 相对亮度公式跑了全部设计令牌两两对比度。`--faint`（#5A657D）相对
`--bg`/`--panel`/`--panel-2` 的对比度分别是 **3.30 / 3.03 / 3.15**，全部低于正文文字
要求的 4.5:1（只够"大字号"门槛 3:1，但 `--faint` 的实际用法几乎全是 11.5–13px 的
小字号：`.metric .k`（style.css:59）、`.sim-metric .k`（105）、`.case-row .lbl`
（93，即病历卡"机理/症状/易发场景/处方/案例"五个标签本身）、`.book-bar`（25）、
`.toc-num`（250）、`table.tbl th`/`td.ch`（230/234）、`.srcref`（213）、
`.case-alias`（89）——覆盖了全站接近一半的"元信息"文字）。CLAUDE.md 把"深色模式
为默认且必须完美"列为硬性要求（"作者常在夜间阅读"），这条失败精确打在这条要求上，
不是可以商量的审美偏好。

进一步核实了修复的难度：`.case-row .lbl`、`.metric .k`、`.sim-metric .k`、
`.book-bar` 这四处用法在 **BASE 段**（逐字抽取自 `sample/ch05-cache-brothers.html`，
用 diff 逐行核对完全一致，0 处差异）；`table.tbl th`/`td.ch`、`.toc-num`、
`.srcref`、`.case-alias`（后两者需确认，多数在 EXTENDED）在 **EXTENDED 段**。
查了近两次 CSS 修复的 commit message（285d90b、8d9cb79），两次都特意写明
"改动位于 EXTENDED 段，BASE 段未动"——说明"BASE 冻结"在这个项目里是被认真
执行的纪律，不是纸面条款，`tools/css-audit.py` 也**没有**脚本层面去校验 BASE
是否与样章一致（读过全文确认），完全靠人自律维持到现在。

**建议做什么：** 不需要引入任何新裸色值——`--muted`（#8A94A9）这个既有令牌对三种
背景的对比度都在 5.8–6.3:1，早就达标，直接复用即可。但要不要动 BASE 段是一个
需要作者明确表态的取舍，不该由执行者悄悄绕过去：

- **保守路径**：只把 EXTENDED 段里的 `--faint` 用法换成 `--muted`（table.tbl
  th/td.ch、.toc-num、.srcref 等）。零风险、不碰 BASE，但治标不治本——病历卡
  标签、指标卡标签这些读者真正要读的小字仍然不达标。
- **彻底路径**：对 BASE 段开一次书面例外，把 `.case-row .lbl` / `.metric .k` /
  `.sim-metric .k` / `.book-bar` 的 `color:var(--faint)` 也换成 `--muted`，
  让 `assets/style.css` 相对样章第一次出现有意为之的差异，并在 CLAUDE.md 或
  README 补一句"为什么"。这是全站对比度真正达标的唯一方式。

**为什么值得做：** 命中 CLAUDE.md 自己写的硬性要求，且失败面很大——不是一两处
边角文字，是病历卡、指标卡、书眉、目录、表头这些反复出现的组件的标签色。

**工作量：小（技术）但需要作者拍板（决策）。** 代码改动是几行 CSS 替换；真正的
成本在于要不要破例碰 BASE，这是我不该替作者做的决定。

### 已核实、不是问题（brief 明确要求列出"哪些无所谓"）

- **决策点/自测按钮语义**：读了 ch05.html 源码，`.opt` 全部是真正的
  `<button class="opt" data-d="1" data-k="bad">`，原生可 Tab 聚焦、可用
  Enter/Space 激活，语义正确，不需要补 role 或 tabindex。
- **canvas 的替代文本**：不是"裸 canvas 零文字替代"——已经有
  `role="img" aria-label="模拟监控图表：DB 请求量、命中率与错误率随时间变化"`
  （ch05.html:148，6 个模拟器逐一核对都有各自贴切的 aria-label），旁边的
  `.sim-metric` 指标卡（命中率/DB 请求量/p99/错误率/状态）用文字实时展示同一份

- **全局 focus 可见性**：grep 了全站 CSS 的 `outline`，没有任何地方写

### 问题 A3（小，选做）：决策揭示没有 aria-live，`.sim-log` 不能用键盘独立滚动

点击 `.opt` 后 `.verdict` 揭示的内容紧跟在按钮组后面（DOM 顺序），继续 Tab 能读到，

## 3. 导航与检索

### 问题 N1：附录只能深链到整章，深链不到具体的病历卡/面试问题，但修复成本比看起来低

`appendix-cards.html`（病历卡图鉴）和 `appendix-interview.html`（面试映射总表）
里所有指向正文的链接都是裸 `href="chNN.html"`（grep 全站核对，零个带 `#anchor`），
而正文里的 `.case-card` 元素本身**一个 id 都没有**（grep `class="case-card"`
逐处核对），`h2` 章节标题也没有 id。全书平均每章 450 行（最长 ch07 524 行，
`wc -l ch*.html` 实测），病历卡通常在第三段、面试映射在第八段（末尾附近），
读者从附录点进去落在页首，得自己滚下去找。

**建议做什么：** 给 `.case-card` 和 `.interview` 里的每个问答块加 id（如
`id="case-07"`），给 h2 加 id，附录 href 改成带 `#case-07`。**这本该是生成步骤，
不是手改**——读了 `tools/derive.py`，它已经在用 `CASE_NO_RE` 正则解析全站的
`.case-no`，也已经在生成 `appendix-interview.html`（`C3` 步骤）。加锚点是给
这条已经在跑的生成管线加一个字段，不是要新开 17+48 处手工编辑，成本比"从零建一套
深链系统"低得多。

**为什么值得做：** 直接命中 brief 问的"深链"缺口，而且现有基础设施把成本摊薄了。

**工作量：小–中。** derive.py 改动本身小；需要设计锚点命名规则、同步改附录生成
模板，改完要过一遍 `validate.py`/`bible-check.py` 确认没破坏既有校验（尤其
`validate.py` 里也在解析 `case-no`，见下面可维护性 V2，两处要一起动）。

### 问题 N2：章内没有任何跳转点，导航只在页首页尾两端

全站没有一处 `position:sticky` 或 `position:fixed`（grep 全站 CSS 确认），
`header` 会随内容一起滚走。而每章固定是 7 个 `<h2>`，每个都带统一格式的编号标签
（如 `05 · 4 模拟器`，`.sec` class，逐章核对格式完全一致）。450 行左右的正文，
移动端一屏能看到的内容更少，读者读到"权衡"段想跳回"病历卡"复习，除了物理上
往上滚一大段没有别的办法。

**建议做什么：** 不需要 sticky 侧栏或复杂 JS——每章 `.chapter-head` 下方加一行
由 7 个 `.sec` 锚点组成的 pill 导航（复用已有的 `.tag-pill` 视觉语言，纯 HTML
锚点链接，不需要额外 JS）。因为 7 段结构和编号已经 100% 规范统一，这行导航本身
可以从每页现有的 h2 文本机械生成，不需要逐页手写措辞。

**为什么值得做：** 缓解"导航只在开头结尾"的问题，设计成本低（复用现成视觉语言
和现成的结构规律，不是新发明一套组件）。

**工作量：中。** 新组件设计 + 23 页都要嵌入，即使是机械生成也要过一遍全站回归。

### 小提示：进度指示目前只有"第几章"，没有"共几章"

`.eyebrow` 已经显示"第 5 章"（.chapter-head 区），但没有"5/16"或视觉进度条。
优先级不高，如果顺手做 N2（章内导航条）可以在同一处一起把总章数带出来，不用

## 4. 性能

### 问题 P1：6 个模拟器的 `setInterval` 永久常驻，不暂停、不响应 reduced-motion

grep 全部 6 个 `assets/sim-*.js`：`setInterval(tick, 100)`（sim-1/2/3/4/6）或
`setInterval(tick, 500)`（sim-5），一旦页面加载就永久运行，零处出现
`visibilitychange` / `IntersectionObserver` / `prefers-reduced-motion`。
全站唯一的 reduced-motion 规则（style.css:16，`*{animation:none!important}`）
只管 CSS `animation`/`transition`（能关掉 `.dot` 的 pulse），管不到 JS 里
`setInterval` 触发的 canvas 重绘——这是两条完全不相交的机制，设置了系统级
"减少动态效果"的用户，进到任意一个模拟器章节，图表依然会以 10 次/秒的频率
持续重绘。同理，读者读完"模拟器"段往下滚到"权衡""复盘"部分后，模拟器已经
滚出视口，但状态机和 canvas 重绘仍在后台跑，直到离开整个页面。

**建议做什么：**
1. `visibilitychange` 监听：标签页切到后台时暂停 tick，切回来恢复；
2. `IntersectionObserver` 监听 `.sim` 是否在视口内，滚出去暂停；
3. 页面加载时检查 `matchMedia('(prefers-reduced-motion: reduce)')`，命中时
   默认不自动播放（等读者主动点"开始"），或明显降频。

**为什么值得做：** brief 点名问的三点（setInterval 常驻/离开页面是否暂停/
reduced-motion 是否处理到位），目前三点全部是"否"。读者边读书边多开几个模拟器
标签页对照前后章节是很自然的阅读方式，CPU/电量成本会叠加；更关键的是
reduced-motion 用户现在完全没有豁免路径，这是可访问性和性能的交叉问题，
不只是"省电"这么简单。

**工作量：中。** 6 个文件都要改，但是同一种模式（可以在 `assets/book.js`
里加一个共用的小 helper，6 个 sim 文件从各自独立的 IIFE 改成调用它——不过这样
也意味着要同时改 6 个文件的接入方式，不是改一处就全站生效）。

### 已核实、不是问题：单页体积

实测：单章 HTML 约 28–32KB（gzip 后约 11KB），`assets/style.css` 19KB（gzip 约
5KB，且 23 页共用同一份，首次加载后全站命中缓存），单个模拟器脚本 5–8KB，
全站没有图片资源。这个量级放在今天任何网络环境下都不构成问题，没有必要为了
"优化体积"去做代码分割或懒加载之类的工程——那会是给不存在的问题找方案，
详见下面"不建议做"。

## 5. 可维护性

### 问题 V2（本视角认为最容易在接手时真正"埋雷"的一条）：同一个正则在 4 个脚本里各自硬编码，改一处忘三处，校验结果会互相矛盾

`class="case-no">病历卡 No.` 这个字符串模式（及其正则变体）被独立硬编码在至少
4 个文件里：`tools/derive.py`（`CASE_NO_RE`）、`tools/validate.py`（两处
`re.findall`）、`tools/bible-check.py`（两处）、`tools/validate_mutation_test.py`。
这 4 个脚本互相不 import，各自对 HTML 做纯字符串/正则解析（不是用 HTML parser），
每个脚本的正则写法还略有差异（有的匹配两位数字 `\d{2}`，有的是 `\d+`）。

这类"坑"最危险的地方不是"新人看不懂"，而是**看起来无害的改动会让 4 个校验脚本
给出互相矛盾的结论**：比如以后想给病历卡加个 data 属性、或者把 `.case-no` 外面
包一层 `<span>`，改的人很自然地只会想到跑一遍 `derive.py` 看它还认不认——
但 `validate.py`、`bible-check.py`、`validate_mutation_test.py` 里那几份正则
不会自动跟着变，可能其中一两个静默地不再匹配任何东西（找到 0 个 case-no，
但因为脚本的容错逻辑不同，有的可能报错、有的可能悄悄把计数当成 0 然后逻辑上
"全部一致"地通过）。新人拿到 4 份不完全一致的校验结果，没有办法判断该信哪个,
也不知道问题出在"正文真的错了"还是"某个正则没跟上"。

**建议做什么：** 抽一个 `tools/_common.py`（或类似的共享模块），把
"解析病历卡编号""解析章节列表""解析面试问答块"这类跨脚本重复的正则/解析逻辑
收进去，4 个脚本改成 `from _common import parse_case_cards` 之类。以后 HTML
结构变了，只要改这一处，4 个脚本自动同步。

**为什么值得做：** 这是最直接回答 brief 第 5 点"交给别人接手最大的坑"的一条——
不是"读不懂这套体系"，是"改了一处、以为改完了，四个校验各给出不同结论，
新人无法判断该信哪个"。而且触发它的改动（换个 class 名、加个属性）恰恰是最常见、
表面上最"看起来无害"的那种改动。

**工作量：中。** 需要仔细核对 4 个脚本里正则的差异是不是有意为之（比如
`\d{2}` vs `\d+` 可能是故意的宽松/严格区别，不能盲目统一），重构完要重跑
`validate_mutation_test.py`（这个脚本本身就是在测试校验器自己，最适合拿来
确认重构没有改变校验行为）确认 10 条规则的变异测试仍然全绿。

### 问题 V1：8 道校验命令全靠人手动按顺序敲，没有一键跑全部、也没有 CI

`README.md` 里列出的验收清单是 8 条独立命令（`validate.py`、
`validate_mutation_test.py`、`bible-check.py`、`css-audit.py`、
`sim-drift-check.py`、`derive.py`、6 个 `node sim*-model-test.js`、
`node --check`），要求按大致固定的顺序手动一条条跑。确认了仓库里没有
Makefile、没有 package.json、没有 `.github/workflows` ——这套投入很重的校验
体系（8 个工具、59 条模拟器断言、还有独立 Codex 七轮终审）目前完全靠人记得
在发布前手动敲完全部 8 条命令，没有任何自动化把关。

**建议做什么：** 加一个 `tools/check-all.sh`，按 README 里的顺序跑完全部 8 步，
任一步失败即非零退出并停止。如果这个仓库将来接了 GitHub remote 用于 Pages 部署，
再加一个 `.github/workflows/check.yml`，在每次 push/PR 时自动跑这个脚本——
不算额外发明，只是把 README 里已经写好的顺序脚本化。

**为什么值得做：** 便宜，且直接堵住"忘了跑某一步就发布"这种最朴素的人为失误，
和这套校验体系本身的严谨程度相称。

**工作量：小。** 脚本本身几行；接 GitHub Actions 如果要做也只是常规配置，
但这个仓库有没有对应的 GitHub remote 需要先确认（README 提到部署到
GitHub Pages，大概率有）。

## 不建议做（至少 2 条，实际给 3 条）

### 不建议 1：客户端全文搜索

**为什么诱人：** 23 页内容,"搜不到自己记得读过的那句话"是读者会自然抱怨的痛点，
brief 也点名问了"搜索"。

**为什么不该做：** 这本书的阅读模式是**线性叙事**（第二人称主角视角、章节间
彼此指涉"第 10 章会正面解决"），不是文档站的"按需检索"模式——CLAUDE.md
明确说这是"系统设计的飞行模拟器"，主线是"秒抢"从 0 到亿级用户的连续故事，
不是可以任意跳读的参考手册。要做好一个静态全文搜索，需要：构建期生成索引
（这个仓库现在"无构建依赖"，加索引生成步骤本身就是一种新增的构建依赖）、
索引要么塞进每页体积（23 页 × 索引大小）要么用 fetch 异步加载（违反 CLAUDE.md
"禁止任何网络请求"的红线）、还要做一个体验过得去的搜索结果 UI 和键盘导航。
对一本以"通读"为设计前提的书，投入产出比很低——单页内查找，浏览器原生
Cmd+F 已经够用；跨页查找的真实需求频率大概率不足以撑起这个功能的维护成本。
如果以后真的需要，交给 GitHub Pages 外部的 Google `site:` 搜索就够了，不用
自建。

### 不建议 2：记住阅读进度 / 断点续读

**为什么诱人：** 16 章的书，"上次读到哪了"是任何内容型产品经理看一眼都会提的
标准建议，而且实现起来看似只是"存一个当前章节到本地"这么简单。

**为什么不该做：** 这个需求的标准实现方式是 `localStorage`（或 cookie），而
`CLAUDE.md` 和 `assets/book.js` 的文件头注释都**明文禁止**："禁止使用
localStorage / sessionStorage / 外部 CDN / 任何网络请求。全部自包含。"
这是这本书的硬性宪法，不是遗漏。之所以把这条单独列出来，是因为它是那种
"看起来是很自然的产品补丁，随手就会有人提"的建议，值得明确记一笔"这条被
项目自己的规则挡住了，不要绕过去用别的存储手段变相实现（比如塞进 URL query
string 当伪书签）"，免得以后哪次有人想"顺手加一下"却没意识到会撞红线。

### 不建议 3：给模拟器加音效 / 触感反馈 / 更多游戏化动效

**为什么诱人：** 六个模拟器是全书交互性最强的部分（真的能"亲手把系统玩坏"），
加点音效反馈（比如 DB 崩溃时的警报音）看起来能强化"这是一场事故"的紧张感，
容易被当成"让模拟器更有代入感"的自然延伸。

**为什么不该做：** 一是和 CLAUDE.md 定的文风红线冲突——"技术原理段落：精确、
不煽情"，模拟器本质是原理演示，不是游戏；二是音效/更多动效会直接叠加到已经
确认存在的 P1 问题（reduced-motion 未处理）之上，给本来就没有豁免路径的用户
群体制造新的、更难关掉的干扰（音频比动画更容易违反可访问性的"不能自动播放
用户未预期的媒体"原则）；三是这是没人要求的"游戏化"范围扩张，不是当前任何
一条真实缺陷的修复。

## 优先级：如果只能做 3 件事

1. **M1 · 模拟器 canvas 移动端各向异性拉伸** —— 影响面最大（6 个模拟器全中）、
   已用实测数据证实是渲染层面的降质而非审美问题，而且正好是项目自己在 README
   里承认"没做过目检"的那个缺口，这次验证证明缺口是真的。
2. **A2 · `--faint` 对比度不达标** —— 直接违反 CLAUDE.md 写明的硬性要求
   （"深色模式必须完美"），覆盖面接近全站一半的元信息文字，技术修复成本很低
   （复用已有的 `--muted` 令牌，不用发明新颜色），唯一的成本是需要作者对
   "要不要碰 BASE 段"表态一次。
3. **V2 · `case-no` 正则四处重复** —— 全部 5 条建议里，这条最直接回答了
   brief 明确问的"交给别人接手时最大的坑"：不是文档不全，是四份互相独立的
   校验逻辑一旦出现分歧，接手的人没有办法判断该信哪一份。

如果能做超过 3 件，**N1（附录深链）和 V1（一键校验脚本）**是紧随其后、
性价比同样很高的两条——都是"利用现有基础设施顺手扩展"，成本比听起来低。
