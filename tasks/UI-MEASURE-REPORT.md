## 1. 测量手段

使用桌面版 Google Chrome 直接打开本地文件：

```text

```

全程通过 Computer Use 操作 Chrome，没有使用 Playwright，也没有用 jsdom 或静态推理代替布局测量。Chrome DevTools Console 中 `document.styleSheets` 返回了本地 `assets/style.css`；DevTools Device Toolbar 的 Responsive 模式分别精确设置为 375×900、768×900、1280×900。每次切换宽度后，在被检查页面的真实渲染上下文中读取 `getComputedStyle()` 和 `getBoundingClientRect()`。

测量对象是 `index.html` 中 `href` 分别为 `ch07.html`、`ch08.html`、`ch09.html` 的三个目标目录行，以及 `href="level2.html"` 的三个-pill 对比目录行。后文中的 rect 顺序均为 `(x, y, width, height)`，单位为 CSS px。

核心测量逻辑等价于：

```js
const tags = [...document.querySelectorAll('.toc-item')]
  .find(a => a.getAttribute('href') === href)
  .querySelector('.toc-tags');
const tagsStyle = getComputedStyle(tags);
const tagsRect = tags.getBoundingClientRect();
const pills = [...tags.children].map(el => ({
  text: el.textContent,
  style: getComputedStyle(el),
  rect: el.getBoundingClientRect()
}));
```

这是 Chrome 的真实 Blink 布局结果；Device Toolbar 只缩放预览画面，不改变被测 CSS viewport 数值，Console 同时确认 `innerWidth` / `document.documentElement.clientWidth` 分别为 375 / 768 / 1280。

## 3. 根因结论

现象成立，但第二个 pill **没有发生 flex 换行**。

- 三个目标行、三个 viewport 下，第二 pill 的水平坐标都严格等于 `第一个 x + 第一个 width + 7px`。例如 1280/ch07：`354 + 117.9296875 + 7 = 478.9296875`。
- 第二 pill 的 `y` 都比第一个大 30px，恰好等于 computed `margin-top: 30px`。
- 目标行第二 pill 同时拥有 `.tag-pill` 与 `.sim`。BASE 把 `.sim` 定义为大型模拟器容器并设置了 `margin:30px 0`；EXTENDED 的 `.tag-pill.sim` 只覆盖边框色与文字色，没有把不适用于 pill 的 margin 归零。
- flex line 本身仍是同一行。第二个 flex item 的 margin box 参与该行布局，但 `getBoundingClientRect()` 返回 border box，所以其可见边框向下偏移 30px；上下 margin 也把 `.toc-tags` 高度从 24.6953125px 撑到 84.6953125px。
- level2 对比组没有 `.sim` 类，三个 pill 的 margin 都为 0，因而三个 `y` 完全相同。

因此根因不是 `gap` 兼容性、`min-width:0`、字体宽度、`line-height` 或真实换行，而是 BASE `.sim` 容器类与 EXTENDED `.tag-pill.sim` 修饰类同名造成的 margin 泄漏。

只修改了 `assets/style.css` 的 EXTENDED 段现有规则，没有修改 BASE，也没有新增裸色值：

